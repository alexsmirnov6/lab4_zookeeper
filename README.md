# Координация расчёта через Apache ZooKeeper

Лабораторная работа 4. Ансамбль из трёх серверов ZooKeeper обеспечивает
согласованное состояние координаторов расчёта пар навыков из ДЗ № 3.

## Отчёт

[Отчёт по ZooKeeper](report/lab4_zookeeper.pdf) содержит конфигурацию стенда,
выводы контрольных команд, снимки Docker Desktop, восстановление из чекпоинта,
оба режима публикации, измерения и ответы на вопросы задания.

Сборка использует сохранённые журналы; повторный запуск экспериментов для неё
не требуется. Генератор сверяет журналы с итогами и эталоном ДЗ № 3.
Для сборки на Windows со стандартными шрифтами Times New Roman и Consolas:

```powershell
pip install -r requirements-report.txt
python report/build_report.py
```

## Ансамбль

Требуются Docker Desktop с Linux-контейнерами и Python 3.12 или новее.
Используется официальный образ ZooKeeper 3.9.6 с Java 17.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
docker compose up -d --wait
python scripts/check_ensemble.py
```

Конфигурация `config/zoo.cfg` общая: список участников должен совпадать.
Серверы получают разные `myid` через `ZOO_MY_ID`. У каждого контейнера свои
тома `/data` и `/datalog`; одинаковые пути внутри контейнеров изолированы.
Клиентские порты на компьютере: 2181, 2182 и 2183, доступны только через localhost.
Внутренние порты 2888 и 3888 не публикуются наружу.

`scripts/check_ensemble.py` проверяет одного лидера и двух последователей,
реальную запись и чтение после остановки одного сервера, недоступность
read-write сессии после остановки двух и восстановление кворума.
Эфемерный узел создаётся штатным `zkCli.sh`; отдельный клиент наблюдает его
наличие и исчезновение после `quit`. Журналы и итог находятся в `logs/ensemble/`.
Скрипт останавливает только контейнеры этого проекта и возвращает все три
сервера в работу даже при ошибке проверки.

```powershell
docker compose exec zk1 zkServer.sh status
docker compose exec zk2 zkServer.sh status
docker compose exec zk3 zkServer.sh status
docker compose exec zk1 zkCli.sh -server zk2:2181
```

Для остановки без удаления данных: `docker compose down`.

## Расчёт и смена координатора

Два Python-координатора считают пары навыков по тем же 6 215 вакансиям, что
в ДЗ № 3. `src/calculation.py` сохраняет правила чтения границ S3 Range GET,
нормализацию навыков и формат `pairs.json` из предыдущей работы. Источник,
коммит и контрольные суммы закреплены в `reference/lab3.json`.

Для существующего каталога `../lab3`:

```powershell
pip install -r requirements.txt
python scripts/prepare_data.py
python -m unittest discover -s tests -v
python scripts/run_failover.py --fencing 0
python scripts/run_failover.py --fencing 1
```

При отдельном клонировании исходный NDJSON можно скачать из закреплённого
коммита. Скрипт подготовки проверит его SHA-256 перед загрузкой:

```powershell
New-Item -ItemType Directory -Path data -Force | Out-Null
Invoke-WebRequest "https://raw.githubusercontent.com/alexsmirnov6/lab3_devops/91d07734e297d2543073923be46f33c9f14eb52b/data/prepared/devops_vacancies.ndjson" -OutFile data/vacancies.ndjson
python scripts/prepare_data.py --source data/vacancies.ndjson
```

Подготовка создаёт локальный `.env` со случайным паролем, если файла ещё нет,
запускает отдельный RustFS и загружает проверенный вход. S3 API доступен на
`http://127.0.0.1:9100`, консоль - на порту 9101. Эти порты не пересекаются с
RustFS из ДЗ № 3. Пароль, состояние Docker и содержимое S3 в Git не включаются.

### Выбор лидера и чекпоинты

Каждый координатор создаёт эфемерный последовательный узел в `/election`.
Лидером становится владелец узла с наименьшим номером; остальные наблюдают
за своим предшественником. При получении лидерства координатор увеличивает
версию `/epoch`. Проверка существования собственного узла и смена эпохи
выполняются одной транзакцией, поэтому потерявший сессию кандидат не может
получить новые полномочия по устаревшему решению о выборах.

Сессия настроена на 10 секунд. После истечения сессии приостановленного лидера
его эфемерный узел исчезает, и запасной получает новую эпоху. Это выборы
координатора приложения; они не меняют лидера самого ансамбля ZooKeeper.

Вход делится на чанки по 65 536 байт; два Mapper-процесса считают локальные
частоты, координатор объединяет их. После каждого принятого чанка он сохраняет
в S3 агрегированные счётчики, число вакансий и множество завершённых чанков.
В ZooKeeper находится только указатель на этот объект с SHA-256. Запасной
проверяет хеш, вход и размер чанка, восстанавливает счётчики и запускает только
оставшиеся задачи. Так уже учтённые чанки не попадают в Reducer повторно.

### Приостановка и публикация

Сценарий ждёт первый чекпоинт и приостанавливает через `docker compose pause`
весь контейнер лидера, включая поток сессии и Mapper-процессы. Обычный `sleep()`
в рабочем потоке не подходит: клиент мог бы продолжать поддерживать сессию.
Задержка 0,3 секунды после каждого чанка включена для эксперимента: без неё
небольшой набор успевает обработаться до приостановки. По умолчанию пауза длится
не менее 40 секунд, и старый лидер возвращается после публикации запасного.

Получатель `src/receiver.py` работает в отдельном контейнере с собственной
активной сессией ZooKeeper. Он принимает ссылку на объект S3 и обновляет
`/result`, одновременно создавая запись в `/publications`. Начальная версия
указателя равна нулю. При `FENCING=0` обе публикации принимаются, и версия
становится 2. Возобновившийся старый лидер записывает устаревшую эпоху последним.

При `FENCING=1` получатель добавляет проверку версии `/epoch` в ту же транзакцию,
которая меняет указатель. Запрос старого лидера получает `BadVersionError`;
указатель сохраняет результат запасного с версией 1. Проверка указателей
чекпоинтов включена в обоих режимах: эксперимент отключает защиту только
публикации результата. После отказа в сохранении чекпоинта старый процесс
заканчивает локальное вычисление и пробует публикацию со своей исходной эпохой.

В S3 могут остаться объекты старого вычисления. Они являются заготовками:
опубликованными считаются только принятые записи `/publications` и указатель
`/result`. Такая схема позволяет отклонить устаревшую публикацию, не перезаписывая
файл запасного координатора.

## Почему три сервера

Операции требуют большинства: для трёх серверов это два. Ансамбль выдерживает
один отказ. Для двух серверов нужны оба, а для четырёх нужны три: четвёртый
сервер не увеличивает допустимое число отказов. Пять серверов выдерживают два.
Три контейнера на одном компьютере демонстрируют отказ процессов, но не
защищают от отказа всего компьютера.

## Почему эпоху проверяет получатель

ZooKeeper знает о завершившейся сессии, но не может остановить зависший процесс
и отменить его последующие запросы к другому сервису. После возобновления такой
процесс всё ещё может закончить вычисления и отправить запись. Если получатель
не сравнит её полномочия с текущей эпохой, смена лидера не предотвратит эту запись.

В этой реализации получатель сам требует проверки эпохи. ZooKeeper выполняет
атомарную проверку версии и обновление указателя, а приложение задаёт, к какой
записи она относится. Проверять эпоху отдельно перед транзакцией нельзя:
между проверкой и записью мог бы смениться лидер. Отдельная сессия получателя
также позволяет показать именно отказ устаревшей эпохи, а не ошибку истёкшей
сессии отправителя.
